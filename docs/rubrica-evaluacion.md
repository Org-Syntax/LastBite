# Rúbrica de Evaluación - Sprint 1 (LastBite)

| Criterio de Evaluación | Excelente (4.5 - 5.0) | Bueno (3.5 - 4.4) | Aceptable (3.0 - 3.4) | Insuficiente (0.0 - 2.9) | Peso |
| :--- | :--- | :--- | :--- | :--- | :---: |
| **Modelado y Base de Datos** | Estructura de BD normalizada o NoSQL óptima. Script funcional sin errores. Relaciones entre comercios, paquetes y reservas correctamente definidas. | BD bien definida con errores menores en tipos de datos o restricciones que no afectan la operación principal. | La BD funciona pero carece de normalización básica o claves foráneas/validaciones clave. | Modelo incoherente, sin script de inicialización o con fallas críticas que impiden la persistencia. | **20%** |
| **Backend y Lógica CRUD** | Endpoints/Rutas CRUD completos para paquetes y reservas. Descuento de stock en tiempo real comprobado y manejo robusto de excepciones. | Backend funcional con validaciones básicas de datos. El descuento de stock opera correctamente en escenarios normales. | El CRUD funciona parcialmente (solo lectura/creación); fallas menores en actualización de inventario. | Errores en el servidor, código no ejecutable o falta de endpoints para el ciclo de reserva. | **30%** |
| **Frontend y UX/UI** | Interfaz totalmente responsiva (Mobile/Desktop), limpia y coherente. Mensajes de error e interacciones visuales claras. | Interfaz responsiva con pequeños desacoples de alineación. Componentes funcionales e intuitivos. | La interfaz funciona pero no es totalmente adaptable a móviles o carece de validaciones en pantalla. | Diseño desestructurado, no responsivo o que dificulta la navegación del usuario. | **25%** |
| **Control de Versiones (Git)** | Commits frecuentes y descriptivos. Estructura de ramas clara (ej. `main`, `develop`, `feature/*`). Sin archivos basura. | Uso de Git adecuado con commits regulares, aunque con mensajes poco explicativos. | POCOS commits en el repositorio o subidos en un único bloque al final del proyecto. | No se utilizó Git o no hay evidencia de control de versiones continuo. | **15%** |
| **Documentación y Sustentación** | Documentos `.md` actualizados (`historia-usuario.md`, `definition-of-done.md`). Sustentación fluida defendiendo la arquitectura. | Documentación completa con detalles menores faltantes. Sustentación clara del funcionamiento general. | Documentación incompleta o entregada a destiempo. Dificultad para explicar partes del código. | Ausencia de archivos de documentación obligatorios o incapacidad para explicar el proyecto. | **10%** |
